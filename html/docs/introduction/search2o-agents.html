Task-focused agents

A Search2o agent is task-focused: it is built for a single task. It runs on the agent server. It does not call other agents. It takes an input, produces an output and finishes in seconds, and it is expected to run thousands of times, for different users.

A Search2o agent has clear boundaries: the systems it can reach, its maximum run time and its LLM cost.

A Search2o agent also carries a plain-language description of the task and its boundaries. Search uses that description to find the agent for a request.

Examples

Typical Search2o agents:

  • Vacation request: takes the dates from the request, checks the leave balance, files the request and reports the result.
  • Invoice status: takes an invoice number and reports where the invoice stands in accounts payable.
  • Expense filing for a trip: retrieves the trip's amounts, files the claim and asks the user before submitting.
  • Part reorder: compares the stock of a part with its reorder point and raises a purchase order with an approved supplier.
  • Support ticket summary: retrieves a customer's open tickets and summarizes the state of each.

Each is one business process: one verb, one or two systems, and a run measured in seconds. The steps are fixed. An LLM does the part that needs language or judgment, such as reading the dates in a request or summarizing a ticket.

The less the tasks of agents overlap, the more easily search matches a request to a single agent.

Why agents are task-focused

Many agents work in a demonstration and fail in production. A general-purpose agent decides its own steps at run time, so the paths it can take are open-ended. A test covers a few of those paths, and real requests then take the others.

A Search2o agent automates one small, well-understood business process and uses LLMs to add intelligence to it. The process fixes the steps, and the LLMs work within them. The agent has only a few paths, so an organization can depend on it to behave in production as it did in development.

Validated before publishing. A developer can run every path of the agent, with every step in the trace, before the agent is published. The inputs of the process are known, and the people who own the process can judge whether the output is correct. See Trace and validation.

Dependable. The agent has only a few paths, and the same request takes the same path through the same commands on every run. The agent that a developer validated in development is therefore the agent that runs in production. A failure has a place: the command it failed at, in the run's record.

Bounded. The agent reaches only the systems its profiles name and stops at its time and cost limits. The agent runtime enforces these boundaries, so they hold however a request is worded. A security team approves one bounded operation, not unrestricted access.

Matched by search. An agent with one task has a precise description. Search matches a request to that description, so users state what they need and do not need to know which agents exist.

Economical. The agent sends an LLM only the instructions and the context of its own task, so it uses few tokens. Search2o is model-neutral: each agent uses its own model, and agents that use different models still work together in one conversation. Models differ in what they do well, so each agent uses the cheapest model that does its task well. A small language model, including one that runs inside the organization, is often enough. A general-purpose agent needs a model capable enough for its hardest request, and pays for that model on every request.

Independent. Each agent is published and versioned separately. A change to one agent is validated on that agent alone, and every other agent keeps running as before. An organization can automate one process, confirm the result, and then move to the next.

Observable. Every run is recorded: who requested it, what ran, how long it took, what failed, and what the LLM calls cost. The reports show these per agent and per user.

What a Search2o agent is not

  • An agent that runs on a person's own machine.
  • An agent built to run for hours or days.
  • An agent run only by the people who built it.
  • A general-purpose agent that decides its own steps at run time, or calls other agents for specific tasks.

How a Search2o agent runs

A request that matches the agent's description starts it; see How matching behaves. The agent runs for a short time, may ask the user for inputs or an approval on the way, and produces a response.

How Search2o agents work together

Search2o agents do not call each other. They build on each other's work through the shared context of a conversation: the prompts and the conversation variables. Two agents share a prompt's history when both have a prompt of the same name with the conversation scope; see Prompts.

A shared prompt history does not depend on the model, so a second agent in the same conversation can use a different LLM and still continue the exchange. Conversation variables carry the context that is not in a prompt, such as the user's authorization.
