Docs / Development process

Publishing

A validated draft can be published. The published agent is visible to every developer and runnable by users, and the draft is retired.

Versions

A publish that changes the definition creates a new version of the agent. Past versions are kept for 7 days and can be viewed from the agent's page. The paid service has no such limit. A publish that changes only the agent meta, that is the prompts, the const, the title or the run limits, keeps the version number; the agent's next run uses the new values. A past version is shown without prompts.

Every publish writes an entry in the audit log, naming the agent, the version and the fields that changed.

When the published agent changed after the draft was made

The title and the run limits can be changed on the agent's page, and another developer's draft can publish new prompts or a new const without a new version. A draft made before such a change still carries the old values. Publishing it first shows which fields differ between the draft and the agent, prompts listed one by one. You can merge those changes into the draft, or publish again to replace them with the draft's values; the changes made on the agent are then lost. In the REST API the second publish carries overwrite.

Describing the agent

After publishing, describe the agent in plain English so that search can find it; see Describing an agent. An agent without a description can be run by name, but search cannot find it.

When several developers change the same agent

Developers who create drafts of the same published agent each work on their own copy. A draft remembers the version it was created from. When someone else publishes a new version of the definition, the draft is behind, and it cannot be published until it is merged.

The next time the draft is opened, the UI says so and offers to merge. The cloud service merges the new version into the draft, saves the result to the draft, and marks the draft as based on the current version. Only the definition is merged. The title, the prompts, the const and the run limits are handled when the draft is published, as described above. In the REST API the same step is the mergeDraft call, offered when getDraft reports that the agent has changed.

If the agent has not changed since the draft was created, there is nothing to merge and publishing proceeds. A draft of a new agent has no published agent to merge with.

How the merge works

The merge follows fixed rules, so the same draft and the same published agent always give the same result. It works one function at a time and never mixes a function from two versions.

FunctionResult in the merged draft
Same in both, or only you changed itYour function.
Only the published agent changed it, or the published agent added itThe published function, without a comment.
Both changed itYour function. The published function is placed above it inside /* ... */ for you to compare.
The published agent removed it and you did not change itRemoved, with a short /* */ note.
The published agent removed it and you changed itYour function, with a note.
You removed it and the published agent did not change itStays removed.
You removed it and the published agent changed itStays removed. The published function is shown inside /* ... */.

A function counts as changed when its content differs. A change to only the layout or the comments of a function does not count. If you changed only the layout or the comments of a function and the published agent changed its content, the published function replaces yours. Functions taken from your draft are kept exactly as typed, including layout and comments.

In this example, you changed the timeout of lookup and the published agent changed its URL.

After a merge

The merge clears the draft's validation. Review each /* ... */ block, copy over what you want, and delete the block. Then validate and publish the draft like any draft. Inside a commented-out function, the characters */ are written as * / so that the comment does not end early.

When a draft cannot be merged

  • A draft that is not valid JSON cannot be merged. Fix the draft first.
  • A definition may be at most 20,480 characters by default. If the merged draft would be longer, the merge is refused, and the draft must be merged by hand.
