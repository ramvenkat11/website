The runtime limits bound a run: how long an agent may run, how many times a loop may iterate, how many rows a database call may return, how long an agent definition may be, and how much an agent may spend on LLM calls. The run time and the LLM cost limits belong to each agent. The other limits are account-wide: developers edit them in the GUI under Guardrails, and they apply to every agent in the account.

How the limits are checked

The limits are checked while the agent runs. Elapsed time is checked between commands, and inside loops every few iterations, as the yield loops after setting says. A run past the time limit ends with the result code timedOut. A long LLM or API call in progress ends only when the call's own timeout fires. A loop that exceeds the iteration limit fails the run. A db command returns at most the row limit. The definition length applies to the JSONC text of a draft, comments included. The stream heartbeat sets how often a streamed response sends a keep-alive line.

LLM cost limit

Each agent carries its own LLM cost limit: the most one run may spend on LLM calls, in US dollars. After every LLM call the agent server prices the call from its token counts and the per-million-token prices in the LLM profile, and adds the amount to the run's total. Once the total passes the limit, the run stops with the result code errorInAgent, and the person is told that the request reached the agent's cost limit. The stop cannot be caught by onError, and it applies inside tool calls and parallel branches. Retries count toward the total. A profile with no prices adds nothing to the total, so a run on such a profile never trips the limit.

The limit is saved with the draft, carried to the agent at publish, and can be changed on the published agent; see Controlled runtime. The cost report shows what each agent's runs spend, which is the evidence for choosing the limit.
