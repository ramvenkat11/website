Search2o encrypts sensitive information before it is stored. You can switch to end-to-end encryption, where only your organization holds the key.

Default: a key managed by Search2o

With encryptionSource set to cloud, Search2o keeps one key per account in a key management service. An agent server fetches the account's key over TLS when the agent server needs it and keeps the key in memory. The agent server encrypts and decrypts; the cloud only stores ciphertext and never decrypts your state. Nothing has to be set up, which is why this is the default. The key exists on Search2o's side, so Search2o, and Google as the infrastructure provider, can in principle read what the key protects.

End-to-end: a key you hold

With encryptionSource set to client, the key never leaves your organization, and nobody outside your organization can read the state or the prompt profiles.

  1. Write an async Python function that takes a key name and returns the key for that name, as 16, 24 or 32 bytes. The function may read a file, an environment variable, or a key management service; anything reachable from the agent server works.
  2. Name the function as the encryptionKey hook, by its dotted path, for example mycompany.keys.get_key. Install the function on every agent server; each agent server imports the function when the agent server starts, and refuses to run agents until a failed import is fixed.
  3. List the keys in keys, each with a name and a creation time. The last key in the list is the current key.

The page refuses to save client until the hook is set, and saving calls the hook once with the current key's name: the save is refused when the hook fails or returns anything but a key of those sizes. From then on the agent server calls your function for every key it needs. The settings are listed below.

Key rotation

Every encrypted value records the name of the key that encrypted it, so several keys can be in use at once. With client-held keys, rotation is adding a new key at the end of the list. The new key encrypts everything from then on. The older keys stay in the list, so that state encrypted under them can still be read. Nothing already stored has to be re-encrypted. An old key is needed for as long as anything encrypted under it is still alive: the plan's retention for a conversation (7 days on Free and 90 days on Paid; a pinned conversation is kept indefinitely), and a year after its last use in a query for a long-term memory (or until the storing agent is deleted).

With the default setting, an administrator rotates the Search2o-managed key from the License page. Rotation issues a new key for the account, and everything already encrypted stays readable — nothing is re-encrypted. Two things to know: an agent server begins using the new key only when the agent server is restarted, and rotation does not protect data already written under a stolen key — rotation bounds future exposure. Rotation is available at most once every 90 days; if a key is known to be exposed, please contact support.

Switching to end-to-end encryption

Switch before the account holds data you care about. State encrypted under the cloud-managed key stays readable after the switch, and new state is encrypted under your key.

What is encrypted

See Data privacy for the full list. Conversation state can also stay in your organization altogether, stored by your own code through the conversation state hooks; the agent server then encrypts nothing on the way out, and encrypting what you store is your choice. The cipher is AES-GCM, and transport between the agent server and the cloud is always TLS.
