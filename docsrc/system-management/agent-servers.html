An agent server is the Python process that runs agents inside your organization. The process is a FastAPI application served by Uvicorn, fully asynchronous, with exactly one worker. Run one agent server on a laptop or several behind a load balancer; any agent server can serve any request. Below: the command line, the addresses an agent server serves, and how agent servers are configured.

The command line

Options on the search2o command line are passed through to Uvicorn, so the Uvicorn options for the address, the port and TLS all work as documented by Uvicorn. A few options are refused because the agent server runs as exactly one worker per process:

--reload --reload-dir --reload-include --reload-exclude --reload-delay --factory --workers

To use more than one worker's worth of capacity, run more agent servers rather than more workers.

What an agent server serves

By default an agent server listens on 127.0.0.1:9020 and serves:

AddressWhat is there
http://127.0.0.1:9020/uiThe GUI
http://127.0.0.1:9020/openapi.jsonThe OpenAPI schema
http://127.0.0.1:9020/docsSwagger UI
http://127.0.0.1:9020/redocReDoc

All of these paths are settings in the agent server's configuration, described next.

Named agent server configurations

The Agent servers page holds one or more named configurations. The configuration named default is required, and an agent server uses it unless told otherwise. To run an agent server under another configuration, append the name to the license key value: SEARCH2O_LICENSE_KEY=your-license-key/edge starts the agent server with the configuration named edge. Use separate configurations when agent servers differ in what they serve, for example an agent server that serves the GUI and an agent server that answers only REST calls.

What a configuration sets

These settings are read once, at startup, so a change takes effect when the agent server restarts. The logs object is a standard Python logging configuration dictionary. The GUI path may point anywhere the agent server can read; leave the GUI path empty to serve no GUI. The documentation paths can be moved or set to nothing to switch the interactive API documentation off.

Startup errors

Problems found at startup are written to the agent server's log. An allowlist entry the agent server cannot import is skipped, and the rest of the allowlist loads. A hook or an LLM adapter that cannot be loaded stops the agent server from running agents until the hook is fixed and the agent server restarted.

Running many agent servers

The agent server is stateless, so you are free to containerize it and run it load balanced; nothing more is needed. Run as many as you need. Every agent server picks up a configuration or profile change before its next agent run, so agent servers never drift from each other; see Agent runtime. The exceptions are the settings on this page, which need a restart, and the license key: after a rotation, every agent server is restarted with the new key.

Health

GET /health is answered by the agent server itself, without sign-in, and is the call for a load balancer or a monitor to use. It reaches nothing outside the agent server, so its response time reflects that agent server's own health. See Agent server sizing.
