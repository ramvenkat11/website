This page reports what one agent server handled under load, so that a deployment can be sized from measurements rather than from guesswork. Everything below is about the agent server, which is the part your company runs. Search2o Cloud scales separately and is not the subject of this page.

How the measurements were taken

One agent server ran on a machine with an Intel Core i9 and 32 GB of memory. The agent server used one of the eight cores, and the rest of the machine was idle.

The account held 100 published agents, each covering a different business domain, so the load ran against a populated account rather than an empty one.

The agent under load is pure logic. It loops, calls a function and sets variables. No language model sits in its path, so the timings below belong to Search2o rather than to a model vendor.

Every level ran for a fixed period. Throughout each level a separate caller measured two other requests, so the tables also show what somebody else felt while the load ran. All measurements come from one session on one day.

Every execution completed at every level, including 150 at once. The product slows down under load and keeps answering.

Throughput peaks at 25 concurrent callers, at 29 executions per second. Adding callers past that point adds waiting rather than throughput: latency rises from 0.755s at 25 concurrent to 4.171s at 150, while throughput stays level or falls.

The core is not what runs out. At peak throughput the agent server used 0.64 of one core. A process that is waiting is not a process that is busy.

What other people feel while the load runs

This is the number to plan against. The question is not how many agents one server can run. The question is how slow the product becomes for everybody else while those agents run.

Browsing took 0.062s on an idle server. It took 0.097s with 10 agents running, 0.227s with 25, 0.501s with 50 and 1.069s with 100.

Ten concurrent agents are invisible to everybody else. Twenty five are noticeable and acceptable. Fifty make the product feel slow to somebody who is only browsing.

Telling which side is constrained

Call a request that the agent server answers by itself. getAccountName is one, because it needs nothing from anywhere else. Call it while the load runs, and read the median. See Agent servers.

A fast answer means the agent server has capacity to spare, and the waiting is elsewhere. Another agent server will not help. That was the case through most of the table above: the request stayed near 0.003s at 100 concurrent callers, while throughput had fallen to 13 executions per second and the agent server was using a third of a core.

A slow answer means the agent server itself is saturated, and another one will help. At 150 concurrent callers the same request took 0.021s, which is eight times its idle figure.

Work that the agent server passes on behaves the same way. Searching for an agent costs an agent server almost nothing, so the rate at which searches complete is set by the capacity behind it rather than by the number of agent servers. A local request that stays fast is the signal for that case.

That one measurement separates the two cases, and it costs nothing to take.

Sizing guidance

Plan for 10 concurrent executions per agent server if nobody should notice a slowdown.

Plan for 25 per agent server if a modest slowdown is acceptable. That level is also where one agent server reached its highest throughput.

Planning for 50 or more per agent server is best avoided. Throughput is no better there than at 25, and people who are only browsing find the product slow.

Add agent servers rather than cores. One agent server is a single process, and a single process uses one core, so a larger machine is mostly spent on processes that an agent server does not start.

It helps to check a local request before adding agent servers. If that request is still fast, the wait is not in the agent server, and another one will not make anything faster.

Keeping measurements comparable

Several things have to stay the same, or two runs cannot be compared.

The set of agents has to stay the same. The account held 100 published agents for every measurement on this page.

The agent under load has to stay the same. An agent that calls a language model spends most of its time waiting for that model, so its timings describe the model vendor rather than the hardware.

The concurrency levels and durations have to stay the same.
