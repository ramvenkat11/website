Search2o gives Claude Code one skill through which it reaches every agent your company publishes. Claude Code chooses which agent runs; it does not write what runs.

Connecting Claude Code to enterprise systems

The usual ways to give Claude Code a company system are an MCP server, or a skill that calls the system directly. Both carry costs that are well known by now.

An MCP server runs as a child process of the assistant and brings its own sign-in, so a person authenticates to every server separately. When something goes wrong, the trace is a JSON transport log rather than a command anyone can rerun. Permissions are granted per tool, with no way to allow a read and refuse a write. Eric Holmes sets these out in MCP is Dead. Long Live the CLI.

A skill that reaches an enterprise system directly raises harder questions.

  • Identity. The connection bypasses the company's identity provider. A skill cannot sign in through OIDC or SAML on its own, so credentials end up hard-coded, or one service account is shared by everyone, against the principle of least privilege.
  • Injection. A skill that queries a database or an API can be steered by text hidden in an email or a document into running commands nobody asked for, or sending data to an outside server.
  • Governance. Skills are uploaded by individual people to individual assistants. The company has no central audit log, no version control and no security patching, and cannot see what is connected to what.
  • Actions. A skill with write access or code execution lets a mistaken or manipulated agent change live tables, delete data or trigger external actions, with no person in the loop.

Skills + Search2o architecture

Search2o sits between your enterprise systems and Claude Code. Claude Code sends the request to Search2o, and Search2o finds and runs an agent built for that request. One skill tells Claude Code when to do so. The skill carries no list of agents and no knowledge of your systems.

Four things follow from that arrangement.

Discovery without context bloat

Claude Code does not hold the agents in its context. When a request arrives, the skill asks Search2o, and search returns the names and titles of the agents that match: at most three lines, whether the company has published ten agents or a thousand. Discovery costs no model tokens. An agent definition never loads into Claude Code at all; the definition stays on the agent server, where the agent runs.

Repeatable workflows, fewer tokens

An agent is a fixed definition. A company developer writes it, a validation run proves it before publication, and every publish is a version. Nothing about the agent changes at run time. Claude Code invokes the agent instead of generating an implementation for each request, so the tokens that went into writing and correcting that code are not spent, and the same request produces the same workflow every time. Inside the agent, each step uses the LLM the developer chose for it.

Contained execution

The agent runs on an agent server inside your organization, in a controlled runtime that limits what it can do. Credentials stay on the agent server, out of Claude Code's context. API responses, database rows and agent variables stay inside Search2o as well. Only the agent's output returns to Claude Code. Code that Claude Code writes locally cannot reach the systems behind the agents.

Central visibility

Every run is recorded by agent, version and person. Administrators can monitor agent executions and their LLM costs in the reports, whether the request came from Claude Code, the GUI or a chat application.

Together, Agent Skills provides the interface and Search2o provides the controlled execution behind it. People work with Claude Code as they already do, while the company defines what its agents can do and which systems they can access. Conversation state is encrypted and saved, so a follow-up request continues where the previous one ended.

Claude Code stands here for every assistant that supports Agent Skills, Cursor among them. The skill is the same.
